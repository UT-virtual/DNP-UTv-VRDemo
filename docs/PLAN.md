### 1.1 リモート接続（インターネット越し）に対応する場合のコスト

Basis の通信層（LiteNetLib / UDP）は、もともとインターネット上のサーバーに接続する前提で作られている。そのため、**通信の仕組み自体を新しく作る必要はない**。コストが変わるのは「どこでサーバーを動かすか」と「ホスト＝助手A という前提をどう扱うか」の2点。

| 方式 | 内容 | クライアントの改修 | 運用・インフラ | 目安 |
|---|---|---|---|---|
| **A. 専用サーバー（推奨）** | クラウドの VPS などで `Basis Server` を動かす（Docker Compose 同梱）。2台ともそのサーバーに接続する | ・接続先アドレスを選ぶ UI<br>・**ロール決定とシナリオの進行管理を「ホスト＝助手A」から切り離す**（ロビーで役を選ぶ方式、進行管理は Basis の所有権（ownership）で決める） | VPS の構築、UDP 4296 の開放、パスワード設定。少額の月額費用がかかる | 3〜5人日 |
| B. ホストモードのまま | 助手A 側のルーターで UDP 4296 をポート開放し、助手B がグローバル IP に接続する | 接続先の入力 UI のみ | ホスト側のネットワークにポート開放と固定 IP（または DDNS）が必要。会場の回線やモバイル回線（CGNAT）では使えないことが多い | 0.5人日。ただし接続できる環境が限られる |
| C. NAT 越え／リレー | ポート開放なしで端末同士を直接つなぐ | Basis にはこの仕組みがないので、マッチングとリレーを自作する | リレーサーバーの運用 | 2週間以上 |

- 方式 A のコストの大半は「ホスト＝助手A」をやめる改修にある。後から対応しやすいように、**ロールの決定とシナリオ進行の権限を判定する処理を1か所（`DemoRoleService`）にまとめ**、ほかのコードは `IsHostMode` を直接参照しないようにする（§2.1）。こうしておけば、リモート対応時に差し替えるのはこのサービスとロビー UI だけで済む。
- 2人で進めるシナリオなので、インターネット越しの遅延（数十〜100ms 程度）による体験への影響は小さい。音声も Basis 標準の Opus 通話をそのまま使える。

## 2. アーキテクチャ

### 2.1 起動〜接続

1. APK を起動すると `DNPDemo_Main` がワールドとして読み込まれる（Basis の起動処理はシーンに依存しない）。
2. **ロビーパネル**（ワールド空間 UI）に「助手A としてホスト開始」「助手B として参加」の2つのボタンを出す。
   - A を選ぶと `BasisConnectionService.ConnectAsync(entry, name, isHostMode: true)` を呼ぶ。
   - B を選ぶと、ホストの IP に接続する。
   - Basis には LAN の自動検出がないので、**簡単な UDP ブロードキャストでホストを見つける仕組みを自作する**。うまく動かない会場向けに、IP の手入力（または設定ファイルや deep link `basisdemo://IP:4296`）を予備として残す。
3. ロールの決め方：ホスト = 助手A、クライアント = 助手B。決まったロールに応じて `Spawn_AssistantA/B` の位置へ移動する。
   - ロールの判定とシナリオ進行の権限判定は `DemoRoleService` に集約する（`GetLocalRole()` / `HasScenarioAuthority`）。現在の実装では、ホストなら助手A かつ進行の権限あり、と判定する。
4. マイクは Basis の初期設定だと**ミュートで始まる**ので、デモではオンで始まるように変更する（プレイヤー同士の会話用）。

### 2.2 シナリオ進行（中核）

```
ScenarioData (ScriptableObject)   … ステップ定義の配列。シナリオの改訂はこのデータの編集で対応する
   └ Step: id / 台詞キュー[] / 完了条件 / 開始時と終了時の演出
ScenarioDirector (BasisNetworkBehaviour)
   ├ 正となる状態（ステップ番号）は進行権限を持つ端末（= 助手A のホスト）が持つ
   ├ ステップ番号は ReliableOrdered で全員に配信する（途中参加の相手には OnPlayerJoined で再送する）
   └ ほかの端末は「アクション完了」を報告するだけ。進行権限を持つ端末が判定してステップを進める
StepCondition（完了条件の種類）
   ├ Timer / CuesFinished … 台詞の再生が終わったら自動で進む
   ├ PlayerAction(role, actionId) … 例：B が複製した、B が肩〜腰を範囲選択した、A が「左手に手鏡」を押した
   └ OperatorSkip … 運営者が強制的に進める（常に使える）
CueSystem … 台詞（音声＋字幕）、モデル差し替え、SE、ライティングを順番に実行する
```

- 状態はすべて「ステップ番号＋少量のイベント」から決まるようにする。像の形や展示台の表示など見た目の状態は、各端末がステップ番号から同じように再現する。これで同期を最小限にでき、通信が乱れても立て直しやすい。
- **運営用デバッグ操作**（隠しパネル、または特定のボタン同時押し）：次へ、戻る、最初からリセット。展示会での体験者交代や不具合からの復旧に必須。

### 2.3 空間選択ペン

助手A・助手B の**右手に1本ずつ常に持たせる**。ペンに描画機能はなく、空間の範囲を選択する道具。

| 要素 | 仕様 |
|---|---|
| 先端スフィア | ペン先に半透明のスフィアを表示する。**右スティックの上下でスフィアの半径を変える**（最小値と最大値を設定）。右スティックの左右は Basis の旋回に使われているので、上下だけを使う |
| 範囲選択 | **トリガーを押している間、スフィアが通った軌跡を半透明の選択範囲としてマークする**。トリガーを離すと1回分の選択が確定する |
| 内部表現 | 軌跡をスフィアのサンプル列（位置＋半径）として記録する。サンプル間隔は半径に比例させる。表示は GPU インスタンシングした半透明スフィア（または生成したチューブメッシュ） |
| 判定 | ステップごとに配置した判定ゾーン（肩、腰、左腕など）とサンプル列の重なりで判定する |
| 同期 | 確定した選択範囲のサンプル列を相手に送り、2人とも同じ選択範囲が見えるようにする（データ量は小さい） |

### 2.4 ステップごとのインタラクション

| 場面 | 担当 | 操作（Quest） | 完了判定 | 演出 |
|---|---|---|---|---|
| ② 像の複製 | 助手B | 像に向けてトリガーを押し、右へスワイプ | トリガーを押したまま一定距離を右へ移動した | 半透明のゴーストが検証台へ移動し、実体化する |
| ③ 円柱の範囲選択 | 助手B | ペンで作業用の像の肩から腰へなぞる | **トリガーを離した時点で、選択範囲が肩ゾーンと腰ゾーンの両方を通っていれば成功**。外れていれば選択範囲を消して、もう一度やってもらう | 選択範囲が黄色いワイヤーの円柱に整形され、認識音のあと大理石の腕（Ver 2.0）へ変形する（ディゾルブ＋スケール） |
| ④ 左手の選択と指示 | 助手A | ペンで左手の部分を選択し、手元パネルの「左手に手鏡」ボタンを押す | 選択範囲が左腕ゾーンに重なるとボタンが押せるようになり、ボタンを押すと完了 | 左腕と手鏡を追加して Ver 3.0 にする |
| 共通：タスク HUD | 各自 | 手元に追従するパネル（ロールごとに内容が違う） | — | 🔔 TASK 表示、達成時のチェック |

- 「AI による生成・修正」は、**事前に用意したモデル同士の遷移演出**で表現する（スキャンライン、パーティクル、ディゾルブ用の Shader Graph）。
- Basis が既に使っているボタン（B/Y＝メニュー、A/X＝ミュートとジャンプ、グリップ＝掴む）と競合しないように、デモ中は不要な機能を無効化する。

### 2.5 学者 NPC・ナレーター

- 学者A/B は **VR 内の NPC** として実装する。台詞は事前に用意した音声（生声または合成音声。台詞ごとに1ファイル）で再生し、頭上に字幕を出す。音源は位置付き（3D）、口パクは Basis 同梱の uLipSync を流用する。
- ナレーターは位置を持たない 2D 音声で、視界の下に字幕を出す。
